# What changed in this pass — SIH26056

## 1. Route basket: 10 routes → 325 routes, one shared source of truth

`shared/generate_routes.py` deterministically builds all C(26,2) = 325
routes across 26 major Indian domestic airports using a gravity model:

    weight(route) ∝ (traffic_mass_A * traffic_mass_B) / max(distance_km, 600)^1

The 600km floor matters: a naive 1/distance gravity model puts short
commuter hops (e.g. BOM-PNQ, 124km) above real long-haul trunk routes,
because it ignores that road/rail absorbs most short-haul demand. With the
floor, the top of the basket is BOM-BLR, BOM-HYD, DEL-BOM, BLR-HYD,
BLR-MAA — genuine major trunk routes, though DEL-BOM lands 3rd rather than
outright 1st. **This is a placeholder methodology, not DGCA data** — the
`methodology` field written into `shared/routes.json` says so explicitly,
and the honest next step is swapping the `AIRPORTS` traffic-mass column for
real DGCA sector-wise passenger traffic figures.

Output: `shared/routes.json` — 325 routes, weights verified to sum to
exactly 1.0.

Verified: `etl-python/route_weights.py` (your uploaded file, unmodified)
loads this file correctly when placed as a sibling of `shared/` — ran it,
confirmed 325 routes loaded and the sum-to-1.0 assertion passes. **This
answers "where does the second file go"**: your repo needs

    <repo-root>/
      shared/routes.json          <- generated by generate_routes.py
      etl-python/route_weights.py <- your file, reads "../shared/routes.json"

`route_weights.py`'s relative path only resolves if it sits in a folder
that is a *sibling* of `shared/` — that's the part that wasn't stated
before.

## 4. Y-axis bug (`components/IndexChart.tsx`)

Root cause: index values carry long float tails (e.g.
`100.77977334310182`); the Y-axis had no `tickFormatter`, so Recharts
rendered full precision and it got clipped by the 40px axis width — that's
the "99999 / 00001" garbage in your screenshot. Fixed with
`tickFormatter={(v) => v.toFixed(1)}` and a slightly wider axis (52px).

## 5. A second, deeper bug in the Supabase path (`app/api/index-data/route.ts`)

Not something you flagged, but real: `route_daily_detail` was fetched with
`.limit(10)` and no date filter. That "worked" only because the sample
basket had exactly 10 routes total — one day's data WAS the whole table.
At 325 routes/day, the moment more than one day of history exists in that
table, `.limit(10)` (or even a bigger number) would start silently mixing
in stale rows from a previous day. Fixed by fetching the latest
`observation_date` first, then filtering `route_daily_detail` to exactly
that date — correct regardless of how much history accumulates. This only
matters once you connect Supabase; it does not affect the sample-data path
you're currently deployed on.

## 6. Scraper, rebuilt on Scrapling (`etl-python/scraper/`) — replaces the `ts-scraper`/Scrapy plan

Confirmed by search before writing any code: the npm package `ts-scraper`
is an unmaintained (last published 2017), single-purpose link-crawler —
not built for "hit one fare page, pull one number," so building on it would
have just recreated the "guessed API, never verified" problem one layer
deeper. [Scrapling](https://github.com/d4vinci/Scrapling) is actively
maintained and a direct fit for the actual failure modes here: adaptive
selectors that relocate themselves when a site's markup changes, a
`StealthyFetcher` for Cloudflare-style bot walls (which IndiGo/MakeMyTrip
likely run), and `capture_xhr` — grabbing the JSON a site's own frontend
already fetched, instead of re-parsing rendered HTML. Recommendation:
consolidate on this one Python/Scrapling scraper; drop both the `ts-scraper`
and the `pip install scrapy` tracks — same job, would only double what you
maintain.

New package: `etl-python/scraper/` —

- `models.py` — the `FareRecord` schema every fare gets normalized into,
  regardless of site or capture method. Has zero dependency on `scrapling`
  on purpose. Includes a sanity-band check (₹1,000–₹1,00,000): rejects a
  record before it ever reaches `anomaly_filter.py`, cheaper than catching
  a parsing bug three stages downstream.
- `xhr_parser.py` — parses a captured XHR/JSON payload. Pure stdlib, no
  `scrapling` dependency, so it's the one part of this scraper that could
  actually be unit-tested in this sandbox.
- `html_parser.py` — CSS fallback via Scrapling's adaptive `Selector`, used
  only when no XHR match fires. Depends on `scrapling` — reviewed, not run.
- `targets.py` — MakeMyTrip + IndiGo target configs, each selector/pattern
  explicitly marked `confidence: "guessed"` — nothing here has touched a
  real site.
- `fare_scraper.py` / `run_scraper.py` — orchestrator (sequential, rate
  limited, exponential-backoff retries) and CLI, wired to read the same
  `shared/routes.json` basket every other consumer reads from.

## 7. Scraper — first real live data captured (2026-09-27)

Ran on the actual user's machine (Windows, real internet access), not this
sandbox. Real findings, not projections:

- **MakeMyTrip: confirmed blocked.** Even with StealthyFetcher's
  `humanize=True` + `geoip=True` enabled, MakeMyTrip served a synthetic
  40-byte placeholder page instead of real content — detected the
  automated browser and soft-blocked it. The identical browser setup
  fetched a real 421KB page from goindigo.in seconds later, confirming
  this is MakeMyTrip-specific defense, not a broken scraper. Downgraded
  from `"guessed"` to `"blocked"` in `targets.py`; deprioritized to a
  stretch goal — would need real residential proxies + heavier
  fingerprint evasion to revisit.
- **IndiGo: confirmed working, real fares captured.** `StealthyFetcher`
  loading `goindigo.in`'s search page triggers a real XHR to a different
  host — `https://6ewai.goindigo.in/r10next/web/fare-radar?origin=DEL` —
  returning clean JSON with real fares (₹3,589–₹9,682 across 6
  destinations from Delhi, captured live). Two things this endpoint does
  that a naive scraper would get wrong:
  1. It's not a point-to-point search — it fans **one origin out to
     several destinations** in a single response, not the one route
     requested.
  2. Its `travelDate` field ("2026-09-28") **did not match** the
     `departureDate` actually sent in the request URL ("2026-10-18") —
     the endpoint appears to ignore that parameter entirely and always
     show near-term fares.

  Wrote a dedicated parser, `extract_indigo_fare_radar()` in
  `xhr_parser.py`, specifically for this verified real shape (the generic
  heuristic parser is kept as-is for other targets, since forcing one
  shape onto a genuinely different JSON structure was producing wrong
  results, not just missing ones). Added
  `real_indigo_fare_radar_2026-09-27.json` — the actual captured response
  — as a test fixture, and 7 new tests in `test_indigo_fare_radar.py`
  built against it. **End-to-end confirmed on the user's machine:**
  `python -m scraper.run_scraper --target indigo --routes DEL-BOM` →
  `fares_found=6`, all real. This is the first genuinely verified,
  non-simulated data point in the whole project.
- **Bug found and fixed via the user's Windows run, not caught in this
  Linux sandbox:** every `open()` call in the scraper lacked an explicit
  `encoding="utf-8"`. On Windows, Python's default file-reading encoding
  is the system codepage, not UTF-8. The test fixture contains a ₹
  symbol; read under the wrong encoding it turned into garbage
  characters — one of which (a "superscript 1", U+00B9) happens to also
  satisfy Python's `.isdigit()` check, silently corrupting the fare
  parser's number-cleaning logic and dropping the whole record. Fixed by
  adding `encoding="utf-8"` to all four file-open calls in the package.
  This class of bug is easy to miss entirely if you only ever develop on
  Mac/Linux (as this sandbox is) — worth remembering for any future
  Python code in this project that touches files with non-ASCII content.

## 7. Index engine — normalize.py, anomaly_filter.py, index_engine.py (`etl-python/scraper/`)

Turns the pile of raw FareRecords a scrape run produces into one
Laspeyres-type index number, in three separable stages (each independently
unit-tested — 11 new tests, 95 total in the suite, all passing):

- `normalize.py` — groups raw fares by route, takes the **median** fare per
  route as the representative price (not min: too gameable by a single
  promo fare; not mean: skewed by the long right tail every route has).
- `anomaly_filter.py` — drops a route's observation if either (a) it moved
  >150% from the last known price for that route, or (b) its price-per-km
  is a robust (MAD-based) outlier vs. every other route scraped in the same
  run. Both checks are skip-safe: a route with no history and too few peers
  this run passes through unfiltered rather than being wrongly flagged.
- `index_engine.py` — Laspeyres-type weighted index using shared/routes.json's
  fixed base_fare/weight per route. **Per explicit product decision**: only
  routes with fresh, anomaly-filter-passed data THIS run count toward
  index_value; the basket weights of whichever routes ARE covered are
  renormalized among themselves so they still sum to 1.0. Routes with no
  fresh data still appear in the dashboard table (falling back to their
  last known price) tagged `source="sample"`, but are excluded from the
  index sum — `coverage_weight_pct` on every result makes this tradeoff
  visible rather than hidden.

`run_pipeline.py` orchestrates all three stages plus (optionally) the live
scrape and a Supabase push — see `--help`. Verified end-to-end against the
real DEL-BOM capture from CHANGES.md §6.3: 57 raw fares -> 1 route
observation -> index 142.19 with 4.0% basket-weight coverage, all numbers
checked by hand.
